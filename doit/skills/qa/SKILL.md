# doit：診斷 QA 回報的問題

QA 回報：$ARGUMENTS

所有回答一律繁體中文（程式碼、指令、識別字除外）。

這個指令把一則 QA 回報變成一份可以直接動手的診斷：問題在哪裡、能不能重現、為什麼發生、怎麼修、修完怎麼確認。修改本身交給 `/doit:go`。

## 硬規則：只診斷不修改

- **不改專案檔案**：不用 Edit、Write、NotebookEdit，也不用 Bash 改檔、不做 commit。為了重現而寫的暫時腳本或測試只放在專案目錄外的暫存目錄，診斷完不留在專案裡。
- **不建立 doit 任務**：不執行 `log.js --new`、`--set`、`--close`、`--lesson`，不寫 `.doit/` 下的任何檔案。
- **執行任何指令前先看副作用**：會寫 DB、打外部服務、寄信、刪資料的，只在確認目標是本機或測試環境時才跑；無法確認就不跑，重現狀態記「無法實跑」與原因。不對 QA 環境或正式環境做任何寫入。
- Bash 一次呼叫只跑一條指令，不用 `;`、`&&`、`||` 串接，不用 `$?`、`$(...)`。
- **沒重現就不說根因確定**：只靠讀程式碼得到的原因標「推論」，不寫成已確認。

## 流程

### 1. 整理回報

把回報整理成五項：**操作步驟、預期結果、實際結果、環境（版本或 commit、瀏覽器或裝置、帳號或資料）、發生頻率**。

- 回報是空的：請使用者貼上 QA 回報，結束。
- 一次貼了多個問題：編號 Q1、Q2…，各自走完下面的流程、各自一份診斷。超過 5 個只做前 5 個，其餘列出標題請使用者分批。
- 缺的項目先自己查（錯誤訊息搜程式碼、git log、截圖或附件裡的文字）。查不到、而且缺了就無從定位或重現的（例如不知道在哪個頁面、沒有實際結果）：一次問完，最多 3 題，停下等回答。其餘缺項照最合理的情況假設，寫進「不確定的地方」。

### 2. 讀背景

- `CLAUDE.md`、`AGENTS.md`、`README.md`（有哪個讀哪個），只取相關部分。
- 教訓（是 git repo 才做）：`node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --lessons`，看這個坑是不是已經記過。
- 找這個功能的需求來源：`.doit/tasks/`、`.doit/archive/`、`.doit/plans/` 裡相關任務的「需求原文」與驗收標準、相關 commit 訊息、規格文件。用來判斷「預期結果」是不是當初講好的行為。

### 3. 定位

- 從回報裡的線索（錯誤訊息、畫面文字、網址、API 路徑、欄位名稱）找到進入點，順著呼叫鏈讀到實際出錯的地方。看實際回傳值與錯誤路徑，不憑名稱猜。範圍大時用 Explore subagent 平行搜。
- 對照版本：QA 測的版本或 commit 與目前 HEAD 之間，相關檔案有沒有改過（`git log <QA 版本>..HEAD -- <檔案>`）。已經在後面的 commit 修掉的，結論就是「已修，請 QA 用新版重測」。
- 找出問題是哪個 commit 引入的（`git log -L`、`git blame`、相關檔案的 `git log`）。是近期某個 doit 任務引入的，記下那個任務與它當初的驗收標準為什麼沒擋住。

### 4. 重現

依序用第一個可行的方式，實際跑出回報裡的「實際結果」：

1. **既有測試或指令**：有測試涵蓋這條路徑，或能用一條指令（CLI、curl 打本機、執行函式）觸發。
2. **暫時腳本或測試**：在專案目錄外的暫存目錄寫一個最小腳本呼叫出錯的函式。
3. **瀏覽器實際操作**：UI 問題照 `${CLAUDE_PLUGIN_ROOT}/skills/go/references/ui-verify.md`「階段 6：怎麼驗」的做法起 dev server、照 QA 的步驟操作、讀實際文字與 console error。自己起的 server 自己停。
4. 都不行（桌面應用、需要真實帳號、依賴拿不到的服務、只在 QA 環境的資料才會發生）：不硬試。

結果只有三種，照實寫：

- **已重現**：寫出跑了什麼、看到的實際輸出，並把它縮成最小重現步驟。
- **未重現**：列出試過的條件，以及最可能造成差異的原因（資料、設定、版本、時序、快取），再列出需要 QA 補什麼才能繼續（例如 request／response、console log、出問題那筆資料的 ID）。
- **無法實跑**：寫原因，並給使用者可以自己照做的重現步驟。

偶發問題（時序、併發、快取）：跑多次，寫「N 次中出現 M 次」。

### 5. 判定

先分類，再談修法：

| 類別 | 意思 | 之後怎麼做 |
|---|---|---|
| 程式缺陷 | 行為與講好的需求不符 | 給修法 |
| 規格如此 | 程式照需求做，QA 預期的是另一種行為 | 不當 bug 修；說明依據，交使用者決定要不要當需求變更 |
| 需求沒講到 | 需求沒定義這個情況 | 列出可選的行為，交使用者決定 |
| 環境或資料 | 程式沒錯，是設定、資料、部署版本的問題 | 寫出要調整什麼 |
| 已修 | 後面的版本已經修掉 | 請 QA 用新版重測 |
| 無法判定 | 資訊不足 | 列出還缺什麼 |

是程式缺陷時再做三件事：

- **根因**：出錯的那一行為什麼錯，寫到「改這裡問題就消失」的程度。區分根因與症狀：在顯示的地方補一個判斷讓畫面正常，不是修根因。
- **同類問題**：用同樣寫法、會有同樣問題的其他地方，搜一遍列出來。
- **影響範圍**：哪些使用者、哪些操作會碰到；資料有沒有已經被寫壞（有的話要另外處理既有資料）；修好之前有沒有繞過的方法。

### 6. 修法與驗證方法

- **修法**：改哪些檔案的哪些函式、怎麼改，並列出這些函式的呼叫者（修了會影響誰）。確實有兩種以上合理做法、而且選擇影響結構、資料格式、相容性或效能時才比較，2～3 個，推薦一個；只有一種就不硬湊。不貼大段程式碼。
- **預估等級**：照 `${CLAUDE_PLUGIN_ROOT}/skills/go/references/tiering.md` 判斷，只是預估，正式定級由 `/doit:go` 決定。
- **驗證方法**三項都要寫：
  1. **回歸測試**：把重現步驟寫成一個測試，寫明放在哪個測試檔、斷言比對什麼具體值。要求是修之前會失敗、修之後通過。專案沒有測試架構時寫明改用哪條指令實跑。
  2. **QA 重測步驟**：給 QA 照做的步驟，網址或畫面、操作、預期看到的具體文字或狀態都要有。
  3. **周邊回歸**：修法動到的函式還有哪些呼叫者，各自要確認什麼沒壞。
- **測試缺口**：既有測試為什麼沒抓到這個問題（沒測這條路徑、斷言太寬、只測了 mock），一句話。

## 回答格式

直接輸出 Markdown，不包在程式碼區塊裡。多個問題時每個問題一份，最後加一張總表（編號、類別、重現狀態、預估等級）。

```markdown
### 🐞 doit:qa：{結論，20 字以內}

{兩三句：這是什麼問題、為什麼發生、建議怎麼處理}

- **類別**：程式缺陷｜規格如此｜需求沒講到｜環境或資料｜已修｜無法判定，加一句依據
- **重現**：已重現｜未重現｜無法實跑，加跑了什麼與實際看到的結果
- **位置**：出錯的地方（`檔案:行`）與從進入點到那裡的呼叫鏈
- **根因**：為什麼錯；沒重現的標「推論」
- **引入點**：哪個 commit 或哪個任務引入；查不到寫「未查到」
- **影響範圍**：誰會碰到、資料有沒有受損、繞過方法、同類問題的位置
- **修法**：改哪裡、怎麼改、會影響的呼叫者；有比較方案時每個一行，最後寫推薦
- **驗證方法**：回歸測試、QA 重測步驟、周邊回歸，各一段
- **測試缺口**：既有測試為什麼沒抓到，一句話
- **不確定的地方**：沒查到、沒跑、採用的假設；沒有寫「無」
- **下一步**：`/doit:go 修正 <問題一句話>：根因在 <檔案:行>，<修法一句話>；驗收：<回歸測試與重測步驟一句話>`
```

- 類別不是「程式缺陷」時，省略「根因」「引入點」「修法」「驗證方法」「測試缺口」中不適用的欄位，「下一步」改寫成該類別的處理方式（請 QA 用哪個版本重測、需要使用者決定什麼、需要 QA 補什麼資料），不給 `/doit:go` 指令。
- 「下一步」的 `/doit:go` 指令要自己帶足資訊（位置、修法、驗收），換一個 session 貼上也能開工。
- 每個關鍵說法都對應到一個來源或一次實際執行。證據寫實際看到的輸出，不寫「符合預期」「已確認有問題」。
- 這個問題是近期某個 doit 任務引入的：在「引入點」註明，並在「下一步」提醒修正任務做檢討時把它記成教訓。
