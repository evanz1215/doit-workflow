# doit：分析報告

分析目標：$ARGUMENTS

所有內容一律繁體中文（程式碼、指令、識別字除外）。跟 `/doit:ask` 的差別：ask 回答一個問題，越短越好；explain 對一個目標寫完整報告並存檔，之後 `/doit:go`、`/doit:plan` 可以引用。

## 硬規則：只讀不改

- **只寫一個檔案**：用 `log.js --new-report` 建立的那份報告。不用 Edit、Write 改其他檔案，也不用 Bash 改檔（重導向寫檔、`sed -i`、`git checkout`、`git commit` 等）。
- **不建立 doit 任務**：不執行 `log.js --new`、`--set`、`--close`、`--lesson`，不動 `.doit/ACTIVE`。
- **只跑沒有副作用的指令**：讀檔、搜尋、`git log`／`git diff`／`git show`／`git blame`、跑既有測試。會寫 DB、打外部服務、刪資料、安裝套件的一律不跑；無法確認安全就不跑，在報告寫「未實跑」與原因。
- Bash 一次呼叫只跑一條指令，不用 `;`、`&&`、`||` 串接，不用 `$?`、`$(...)`。
- 使用者其實是要求修改：不要動手，在報告「結論」寫怎麼改、影響哪裡，回報附 `/doit:go` 指令。

## 做法

1. **目標是空的**：請使用者說明要分析哪個檔案或功能，結束。
2. **判斷目標類型**：
   - **檔案／模組**：給的是路徑，或是明確的模組名。先確認檔案存在；不存在就搜尋相近的檔名，找到一個就用它並在報告註明，找到多個或找不到就列出來請使用者選，結束。
   - **功能**：給的是行為描述（例如「登入怎麼做的」）。先找入口（路由、事件處理、CLI 指令、匯出的 API），找到多個彼此無關的入口時請使用者縮小範圍。
3. **讀專案慣例**：`CLAUDE.md`、`AGENTS.md`、`README.md`（有哪個讀哪個），只取與目標相關的部分。
4. **讀教訓**（是 git repo 才做）：`node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --lessons`，挑相關條目。
5. **查原始碼**：
   - 讀目標全文，不只看名稱。函式要看實際回傳值與錯誤路徑。
   - 找所有呼叫者（import、引用、字串式的動態引用如 store id、事件名、路由名），不要只找第一個。
   - 找測試、設定、型別定義；外部套件先看 lock 檔確認安裝版本。
   - `git log --oneline -n 10 -- <檔案>` 看最近怎麼演變，有助於解釋「為什麼長這樣」。
   - 呼叫者很多或功能跨很多目錄時，用 Explore subagent 平行搜。
6. **能驗證就驗證**：有既有測試覆蓋目標就跑一次，報告寫跑了什麼、結果如何。
7. **落檔**：`node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --new-report <slug>` 建立骨架（會自動把 `.doit/` 排除在 git 外）。slug 用英文小寫與連字號，取自目標（例如 `breakpoints-store`）。再用 Edit 把每一節填好（格式見下）。
8. **回報**：依「回報格式」輸出，然後停下。

## 報告格式

骨架的每一節都要有內容；不適用的寫「無」加一句原因，不要刪標題。

- **分析目標**：使用者原話；實際分析的檔案或入口（`檔案:行`）；目標類型（檔案／功能）。
- **結論**：三到五句。這是什麼、怎麼運作、最值得注意的一件事。讀者只看這一節也要懂。
- **職責**：它負責什麼、不負責什麼（邊界在哪、交給誰）。
- **對外介面**：
  - 檔案／模組：匯出的函式、類別、state、getter、action、事件，每個一行：名稱、用途、型別或參數。
  - 功能：入口（使用者或系統怎麼觸發）與最終結果（畫面、回應、寫入的資料）。
- **誰在用**：呼叫者清單，每個一行 `檔案:行` 加用法；多於 10 個時依用法分組，每組列代表性的 2～3 個並寫總數。功能類型改寫成**呼叫路徑**：入口 → 經過的檔案與函式 → 結果，一行一跳。
- **運作流程**：初始化、主要流程、狀態何時改變。流程有分支或非同步時用編號步驟寫清楚順序；有助於理解時可以加一張 mermaid 圖。
- **依賴**：用到的內部模組與外部套件（套件附 lock 檔裡的版本），以及它依賴的環境（瀏覽器 API、環境變數、全域設定）。
- **邊界與風險**：實際看到的邊界處理與缺漏，例如 SSR／沒有 window、空值、併發、事件監聽沒移除、錯誤被吞掉。每條附 `檔案:行`。只寫在原始碼看到的，推論要標明是推論。
- **測試**：有哪些測試覆蓋它（檔案路徑）、實跑結果、哪些行為沒有被測到。
- **依據**：主要讀過的檔案與跑過的指令和結果。
- **不確定的地方**：沒查到、沒跑、推論而非直接看到的部分；沒有寫「無」。

寫法：

- 每個關鍵說法都要對應到 `檔案:行` 或一次實際執行。
- 不要貼大段原始碼，引用位置就好；必要時節錄幾行。
- 寫給之後要改這段程式的人看：重點是「改它之前要知道什麼」，不是逐行翻譯。

## 回報格式

直接輸出 Markdown，不包在程式碼區塊裡：

```markdown
### 📄 doit:explain：{目標名稱}

{報告「結論」一節的內容}

- **報告**：`.doit/reports/<檔名>.md`
- **最值得注意**：{邊界與風險裡最重要的一條，沒有就省略這行}
- **下一步**：{使用者的話指向要修改時才有，附可以直接貼的 `/doit:go <開發指令>`}
```
