# doit：唯讀回答問題

問題：$ARGUMENTS

所有回答一律繁體中文（程式碼、指令、識別字除外）。

## 硬規則：只讀不改

- **不改任何檔案**：不用 Edit、Write、NotebookEdit，也不用 Bash 改檔（重導向寫檔、`sed -i`、`git checkout`、`git commit` 等）。
- **不建立 doit 任務**：不執行 `log.js --new`、`--set`、`--close`、`--lesson`，不寫 `.doit/` 下的任何檔案。
- **只跑沒有副作用的指令**：讀檔、搜尋、`git log`／`git diff`／`git show`、跑既有測試。會寫 DB、打外部服務、刪資料、安裝套件的一律不跑；無法確認安全就不跑，在回答裡寫「未實跑」與原因。
- Bash 一次呼叫只跑一條指令，不用 `;`、`&&`、`||` 串接，不用 `$?`、`$(...)`。
- 問題其實是要求修改（例如「幫我把 X 改成 Y」）：不要動手，回答怎麼改、影響哪裡，並加上「下一步」欄建議用 `/doit:go` 執行。

## 做法

1. **問題是空的**：請使用者說明要問什麼，結束。
2. **讀專案慣例**：`CLAUDE.md`、`AGENTS.md`、`README.md`（有哪個讀哪個），只取與問題相關的部分。
3. **讀教訓**（是 git repo 才做）：`node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --lessons`，挑與問題相關的條目，回答時提到。不是 git repo 就略過。
4. **查原始碼**：找相關的實作、呼叫者、測試、設定。使用函式前看實際回傳值與錯誤路徑，不憑名稱猜。查外部套件前先看 lock 檔確認安裝版本。範圍大時可以用 Explore subagent 平行搜。
5. **能驗證就驗證**：結論可以用一個唯讀指令或既有測試證明時，實際跑一次，回答寫跑了什麼、結果是什麼。
6. **多個方案**：只有在確實有兩種以上合理做法、而且選擇會影響結構、資料格式、相容性或效能時才比較。2～3 個，推薦一個，理由要連到這個專案的實際情況。只有一種合理做法就不硬湊。
7. 回答。

## 回答格式

直接輸出 Markdown，不包在程式碼區塊裡：

```markdown
### 💬 doit:ask：{結論，20 字以內}

{兩三句直接回答問題，寫成一般段落，不用條列}

- **依據**：支撐答案的原始碼位置（`檔案:行`）與實際跑過的指令和結果
- **不確定的地方**：沒查到、沒跑、推論而非直接看到的部分；沒有寫「無」
```

固定的只有三樣：標題、開頭的回答段落、「依據」與「不確定的地方」兩欄。簡單的問題到這裡就結束。

以下欄位**只在適用時出現**，不適用就整欄省略，不要寫「無」來湊：

- **細節**：兩三句講不完時才加，放在回答段落之後、「依據」之前，條列展開（例如分情況、分步驟）。結論仍然留在開頭的段落，不要搬進這一欄。
- **方案比較**：確實有多個合理做法時才有。每個方案一行：做法、優點、缺點；最後一行寫推薦哪個與理由。
- **相關教訓**：教訓條目真的影響了答案才寫，附編號與一句話。只是讀過、與問題無關的不提。
- **下一步**：問題本身指向要修改時才給，附可以直接貼的指令，例如 `/doit:go <開發指令>`。
- **順帶發現**：查的過程中看到、但使用者沒問的問題，最多一行，只描述現象。不要為它附 `/doit:go` 指令，也不要放進「下一步」。

寫法：

- 標題只放結論，一個重點，20 字以內；放不下的進回答段落。
- 答案要能被檢查：每個關鍵說法都對應到一個來源或一次實際執行。推論要標明是推論。
- 不要貼大段原始碼，引用位置就好；必要時節錄幾行。
