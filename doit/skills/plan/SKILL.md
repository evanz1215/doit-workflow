# doit：把大需求拆成多個任務

需求：$ARGUMENTS

所有回報與計畫檔內容一律繁體中文（程式碼、指令、識別字除外）。

`/doit:go` 一次處理一個最多 5 步的任務。需求大到要拆、或模糊到還不知道怎麼做時，先用這個指令規劃。產出是一份計畫檔，之後一個一個任務用 `/doit:go` 執行。

## 硬規則：只規劃不實作

- **不改專案檔案**：不用 Edit、Write 改 `.doit/plans/` 以外的任何檔案，也不用 Bash 改檔、不做 commit。
- **不建立 doit 任務**：不執行 `log.js --new`、`--set`、`--close`，不動 `.doit/ACTIVE`。計畫檔不是任務檔，hooks 不管它，所以這條靠你自己遵守。
- **只跑沒有副作用的指令**：讀檔、搜尋、`git log`／`git diff`、跑既有測試。會寫 DB、打外部服務、刪資料、安裝套件的不跑。
- Bash 一次呼叫只跑一條指令，不用 `;`、`&&`、`||` 串接，不用 `$?`、`$(...)`。
- 需求其實很小（單一功能、五步以內做得完）：不用拆，直接告訴使用者用 `/doit:go <需求>`，結束。

## 好計畫的標準

寫完自己對照一次，每一條都要成立：

1. **沒看過這次對話的人也能照著做**：每個任務的 `/doit:go` 指令加上計畫檔，就足以開工。
2. **每個需求都落在某個任務裡**：把需求拆成一句一句，每句對得到任務的驗收重點。對不到的不是漏了就是該列進範圍外。
3. **假設對照過程式碼**：描述既有程式行為的假設，先看程式碼或實際跑一次，標「已查證」附位置；查不了才標「未查證」附原因。
4. **需要使用者決定的事攤開來**：會改變使用者看得到的行為、或影響多個任務的決定，獨立列在「需要你決定」，寫出預設、另一個選擇、差別。
5. **範圍邊界明確**：不做什麼、既有行為哪裡會變，寫出來。
6. **短**：計畫檔講決定與邊界，不寫實作細節、不貼程式碼。每個任務的細部計畫留給 `/doit:go`。

## 流程

每個階段結束都輸出一份給使用者看的回報，再往下做（格式見「回報格式」）。

### 1. 前置

- 必須是 git repo，不是就告知並停止。工作目錄不乾淨沒關係，這個指令不改專案檔案。
- 讀 `CLAUDE.md`、`AGENTS.md`、`README.md`、`CONTRIBUTING.md`（有哪個讀哪個），整理相關慣例。
- 讀教訓：`node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --lessons`，挑相關條目。
- 找測試、lint、build 指令與來源檔案，記下來給各任務用。不用跑基準，每個任務的 `/doit:go` 會自己跑。

### 2. 探索

- 讀相關程式碼、類似的既有實作、相關測試。範圍大時用 Explore subagent 平行搜。
- 找出會被改到的模組、介面，以及它們的呼叫者。
- 找出現有結構對做法的限制（資料格式、對外介面、既有慣例）。

### 3. 釐清

- **阻擋型疑問**（答案相反時整個拆法要重來）：先問，一次問完，最多 5 題，每題附建議答案與理由。問完停下等回答。最多兩輪，之後仍沒回答的寫進計畫檔「需要你決定」並標明「未回答，暫採預設」。
- **非阻擋型**：寫進「假設」或「需要你決定」，附預設。
- 能從程式碼、文件、git log 查到的自己查，不拿來問。

### 4. 做法

- 有兩種以上合理做法、而且選擇影響結構、資料格式、相容性或效能時，比較 2～3 個，推薦一個，理由連到這個專案的實際情況。只有一種合理做法就不比較。

### 5. 拆任務

- 每個任務是一個 `/doit:go` 能獨立完成、獨立驗證的單位：一個可觀察的成果，預估五步以內。
- 依賴順序排好。每個任務只依賴排在它前面的任務。做完任何一個任務，專案都要處在可以運作的狀態（測試會過），不能有「做到一半要等下一個任務才能跑」的任務。
- 風險高的部分（改資料結構、權限、對外介面、刪資料）盡量獨立成一個任務，不要和低風險的改動混在一起，這樣只有它需要走高風險流程。
- 先做能最早暴露問題的任務（例如最不確定的技術點），不要留到最後。
- 2～7 個任務。超過 7 個代表需求該再分期，在「範圍外」列出後面幾期。

### 6. 落檔

1. `node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --new-plan <slug>` 建立計畫檔骨架（會自動把 `.doit/` 排除在 git 之外）。slug 用英文小寫與連字號。
2. 用 Edit 把內容填進對應的節（格式見「計畫檔格式」）。
3. 對照「好計畫的標準」六條自我檢查一次，不成立的改掉。

### 7. 交付

依「回報格式」輸出最後一份回報，然後停下。不要自己開始執行任何任務。

使用者之後要求修改計畫時：直接改計畫檔對應的節，在「變更紀錄」加一行（日期、改了什麼、為什麼），重新輸出交付回報。

## 計畫檔格式

骨架由 `log.js --new-plan` 建立，照下面的寫法填。不適用的節寫「無」，不要刪掉標題。

```markdown
# 計畫：<slug>

- 建立：<日期時間>
- 狀態：草稿 | 已確認 | 進行中 | 完成

## 需求原文
<只放使用者真的說過的字，逐字>

## 現況
<探索結果：相關模組與它們的呼叫者（檔案:行）、現有結構的限制、可用的測試／lint／build 指令與來源檔>

## 做法
<三五句：整體怎麼做、為什麼這樣做>
<有比較方案時：每個方案一行（做法、優點、缺點），最後寫推薦哪個與理由>

## 需要你決定
- D1 <疑問> → 預設：<做法>；另一個選擇：<做法>；影響：<差別，以及會影響哪些任務>

## 假設
- <假設> → 預設：<做法>（已查證：<檔案:行 或 跑過的指令>）
- <假設> → 預設：<做法>（未查證：<原因>）

## 任務清單

| # | 任務 | 預估等級 | 依賴 | 狀態 |
|---|---|---|---|---|
| T1 | <一句話成果> | 低／中／高（<命中條件>） | 無 | 待開始 |
| T2 | ... | ... | T1 | 待開始 |

### T1 <任務名稱>
- 目標：<做完之後可以觀察到什麼>
- 範圍：<會動到的檔案或模組>
- 驗收重點：<兩三條可觀察的結果，/doit:go 會把它們展開成正式的驗收標準>
- 相關決定：<D 編號與假設，沒有寫「無」>
- 指令：`/doit:go 依 .doit/plans/<檔名> 的 T1：<一句話任務說明>`

## 範圍外
- <不做的事>，理由

## 風險與未知
- <還不確定的事、可能讓計畫要改的情況，以及哪個任務會先碰到它>

## 變更紀錄
- <日期> 建立
```

- **預估等級**照 `${CLAUDE_PLUGIN_ROOT}/skills/go/references/tiering.md` 的條件判斷，只是預估；正式定級由該任務的 `/doit:go` 在看過呼叫者之後決定，只會維持或升級。
- **指令**一定要帶計畫檔路徑與任務編號，`/doit:go` 才會去讀這份計畫。

## 回報格式

直接輸出 Markdown，不包在程式碼區塊裡。前置、探索、釐清、做法、拆任務各一份簡短回報：

```markdown
### 🗺️ doit:plan {階段名稱}：{這個階段的結論}

- **完成**：這個階段得到的結果
- **問題**：遇到什麼、還沒解決的；沒有寫「無」
- **下一步**：接下來做什麼
- **需要你處理**：要使用者回答的事；不需要寫「無，自動繼續」
```

交付時的最後一份可以長一點，使用者不開計畫檔就能判斷：

```markdown
### 🗺️ doit:plan 完成：{幾個任務、整體做法一句話}

{兩三句：這份計畫怎麼達成需求}

- **需要你決定**：每項一行（預設、另一個選擇、差別）；沒有寫「無」
- **任務**：依順序每個任務一行：編號、成果、預估等級、依賴
- **未查證的假設**：逐條列出；沒有寫「無」
- **範圍外**：逐條列出
- **風險與未知**：逐條列出；沒有寫「無」
- **計畫檔**：`.doit/plans/<檔名>`
- **下一步**：回覆要修改的地方，或直接執行第一個任務：`/doit:go 依 .doit/plans/<檔名> 的 T1：…`
```
