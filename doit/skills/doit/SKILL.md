# doit：依風險分級的開發工作流（v0.1）

把開發指令變成一次有證據、可回退、可接續的交付。

**語言**：所有回報、計畫、任務檔紀錄、commit 訊息一律繁體中文（程式碼與指令除外）。

**v0.1 範圍**：低／中風險、brownfield、一般模式。判成高風險時仍可走，但高風險專屬關卡（plan-critic、fresh implementer、verifier、瀏覽器驗證）尚未實作，要明確告知使用者並以中風險流程加「每步必回報」處理。`auto`、`new` 子指令尚未實作，收到時告知並改走一般模式。

指令：$ARGUMENTS

## 分派

| `$ARGUMENTS` | 做什麼 |
|---|---|
| 空白 或 `resume` | 走「接續」；沒有進行中任務時請使用者說明要做什麼 |
| `status` | `node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --show`，再摘要狀態、下一步、驗收標準證據進度 |
| `abort` | 確認後 `log.js --close 中止 "[停止] 使用者中止：<原因>"`，不動分支與程式碼 |
| `auto ...` / `new ...` | 告知 v0.1 尚未支援，詢問是否以一般模式繼續 |
| 其他 | 新任務，從階段 0 開始 |

## 三條硬規則（hooks 會強制，skill 只是說明）

1. **未批准不動手**：任務狀態在「已批准」之前，Edit/Write 專案檔案會被 hook 擋下。
2. **未達門檻不交付**：完成門檻（`references/review.md`）沒過，狀態不是「完成」時，非 `wip:` 前綴的 `git commit` 與任何 `git push`/`merge` 都會被擋下。
3. **離開前存狀態**：有進行中任務時，「下一步」欄位是空的就無法結束回合。

## 任務檔與寫入工具

- 任務檔在 `.doit/tasks/<日期>-<slug>.md`，`.doit/ACTIVE` 指向它。不進 git。`.doit/` 不是敏感目錄，Edit/Write 不會被擋。
- **頂端欄位與紀錄行一律用 log.js 寫**（有格式驗證、自動時間戳、自動插到「## 紀錄」小節）。
- **其餘小節直接用 Edit 寫**：填「需求原文」「基準檢查」「影響範圍」三節的內容，以及在檔尾追加 `## 計畫 vN`。不要用 node -e、`cat >>` heredoc 或其他 shell 腳本改任務檔：長段含反引號與表格的 Markdown 會被 Bash 工具的解析器拒跑。
- 不確定用法時 `node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --help`。

```bash
node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --new <slug> --set 類型=feat
node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --set 狀態=待批准 --set "下一步=等使用者批准計畫 v1"
node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" "[完成] 步驟 1：新增 parsePage()" "[證據 標準2] npm test -- pagination 通過"
node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --show
```

標籤：`[完成]` `[紀錄]` `[證據 標準N]` `[錯誤 來源：agent|使用者|環境 分類：需求|實作|工具|環境|流程]` `[審查 …]` `[批准 vN]` `[升級]` `[停止]` `[範圍外]`。格式見 `references/plan-format.md`。

## 參考檔（到該階段再讀）

| 檔案 | 何時讀 |
|---|---|
| `${CLAUDE_PLUGIN_ROOT}/skills/doit/references/tiering.md` | 階段 2 初判、階段 3 定級、實作中懷疑要升級時 |
| `${CLAUDE_PLUGIN_ROOT}/skills/doit/references/plan-format.md` | 階段 3 寫計畫前；接續時 |
| `${CLAUDE_PLUGIN_ROOT}/skills/doit/references/review.md` | 階段 7 審查、階段 8 完成門檻 |
| `${CLAUDE_PLUGIN_ROOT}/skills/doit/references/retro.md` | 階段 9 檢討 |

## 接續

1. `log.js --show`。狀態是「完成」或「中止」就當作沒有進行中任務。
2. 檢查：目前分支等於「分支」欄（「尚未建立」則應在 base 上）；「起始SHA」是 HEAD 的祖先（`git merge-base --is-ancestor <sha> HEAD`）；工作目錄狀態與最後幾行紀錄相符。不符就列出差異問使用者，不自動修。
3. 依「狀態」與「下一步」繼續。**狀態「待批准」時重新提交計畫等批准，不能直接開工**；「待使用者」且計畫版本 0 時重新列出未回答的釐清問題。

## 階段 0：前置檢查

- 必須是 git repo。不是就告知並停止（建議 `git init` 後 commit 一次再來）。
- `git status --porcelain` 必須為空（`.doit/` 已排除）。不乾淨就請使用者自己 commit 或 stash，不要替使用者決定。
- 記下 **base 分支**與**起始 SHA**（`git rev-parse HEAD`）。之後「完整變更」一律以起始 SHA 為基準。
- 讀 `CLAUDE.md`、`AGENTS.md`、`README.md`、`CONTRIBUTING.md`（有哪個讀哪個），整理與這次任務相關的慣例與禁止事項。
- 從 `package.json` / `pyproject.toml` / `Makefile` / `go.mod` / CI 設定找測試、lint、型別檢查、build 指令，**記下來源檔案**。找不到的不猜，列為「無基準」並在計畫中標明。
- **執行任何指令前先看副作用**：會寫 DB、打外部服務、寄信、刪資料的，只在確認目標是本機或測試環境時才跑；無法確認就不跑，記為未驗證。
- 跑一次基準檢查（lint + 相關測試；夠快就全跑），結果寫進任務檔 `## 基準檢查`。
- 讀教訓檔：`node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --lessons` 會印出專案（`.doit/LESSONS.md`）與全域（`~/.doit/LESSONS.md`）兩份；全域檔在專案目錄外，不要用 cat 或 Read 直接讀。挑相關條目照做。
- 建立任務檔：`log.js --new <slug> --set 類型=<type> --set base=<分支> --set 起始SHA=<sha> --set "下一步=探索"`。類型：feat / fix / refactor / test / perf / docs / chore。

## 階段 1：探索（只讀不改）

- 讀相關程式碼、類似的既有實作、相關測試。範圍大時用 Explore subagent 平行搜。
- 找出被修改函式／介面的**所有呼叫者**，寫進任務檔 `## 影響範圍`。這是分級依據。
- 使用既有函式前看實際回傳值與錯誤路徑，不憑名稱猜。
- 查外部文件前先看 lock 檔確認實際安裝版本。
- 探索中發現階段 0 沒跑到的相關測試，**改任何程式碼之前**補跑，追加到基準。

## 階段 2：釐清需求

疑問分兩類：

- **阻擋型**：答案若與猜測相反，計畫要重寫一半以上（做法、範圍、資料結構、對外行為）。**寫計畫前就問**。
- **非阻擋型**：只影響細節、有合理預設。寫進計畫「假設」欄附預設做法。

以下一律算阻擋型：刪除／覆寫／清除資料時是軟刪還是硬刪；新增權限規則時誰可以做。

規則：能從程式碼、文件、git log 查到的自己查；一次問完（最多 5 題）、每題附建議答案與理由；停下前 `--set 狀態=待使用者 --set "下一步=等釐清回答"`；最多兩輪，之後列為「未釐清（阻擋）」，批准時使用者必須逐項選。沒有阻擋型疑問就直接往下，不硬湊。

## 階段 3：計畫落檔

先讀 `references/tiering.md` 定級、`references/plan-format.md` 看格式，然後把 `## 計畫 v1` 追加到任務檔尾端。

- **方案比較**：有兩種以上合理做法、且選擇影響結構／資料格式／相容性／效能時才寫，2–3 個選項，推薦一個並連結到這個專案的實際情況。只有一種合理做法就不比較。
- **驗收標準**：每條要能被測試或實際執行證明，並寫明怎麼證明。使用者看得到的行為改變至少一條要寫「怎麼看到它」（既有 e2e／元件測試 → 瀏覽器實際操作 → 都沒有就寫「需使用者手動確認：頁面、操作、預期結果」）。
- **實作步驟**：以「做完能用一個測試或一次執行證明」為單位，2–5 步，每步只依賴前面的步驟。驗收標準每一條都要落在某一步的驗證裡。
- **範圍外**：實作時碰到只能記 `[範圍外]`，不能順手做。
- **需求原文**只放使用者真的說過的字。
- 定級後 `--set 等級=<級> --set 命中條件=<條件或無> --set 計畫版本=1 --set 狀態=待批准 --set "下一步=等使用者批准計畫 v1"`。
- 判成高風險：告知「v0.1 高風險關卡尚未實作，將以中風險流程處理並每步回報」，使用者同意才繼續。

## 階段 4：批准

- **只有明確同意才算**：「確認」「照計畫做」「OK 開始」。問句、部分回答、「嗯」都不算，先回答再追問一句：「我會照計畫 v<N> 開始：<摘要，含非阻擋型假設的預設>。確定嗎？」
- 有「未釐清（阻擋）」時，整體同意不算，要逐項回答完才算。
- 批准後：`log.js --set "批准=v1「<使用者原話>」" --set 狀態=已批准 --set "下一步=開分支並做步驟 1" "[批准 v1] 「<原話>」"`。非阻擋型假設沒被逐項回答時，紀錄寫「假設『…』未明確回答，採計畫預設」，不要寫成「使用者已同意某做法」。
- 使用者修改計畫：追加 `## 計畫 v<N+1>`（寫明差別），`--set 計畫版本=<N+1> --set 批准=無`，重新定級（只能升不能降），再提交等批准。使用者的修正記 `[錯誤 來源：使用者 分類：需求]`。

## 階段 5：實作

- 開分支 `<type>/<kebab-name>`，`--set 分支=<名稱> --set 狀態=實作中`。已在非主幹分支時問是否沿用。
- 逐步做，每步做完跑該步的驗證，記 `[完成] 步驟 N：…` 與 `[證據 標準N] …`。
- **中風險每步做檢查點 commit**：`git commit -m "wip: 步驟 N <摘要>"`。低風險可省。
- 碰到計畫沒涵蓋的情況：小偏差記 `[紀錄]` 繼續；要改做法、範圍、資料結構的，停下來重提計畫（回階段 3）。
- 實作中發現影響超出定級（例如要改有呼叫者的函式、要動 schema）：`[升級]` 記下，依 `tiering.md` 升級，告知使用者。
- 同一步驗證連續失敗 3 次 → 停，記 `[錯誤]`，回報使用者，不再硬試。
- 每步更新「下一步」。

## 階段 6：驗證

- 跑計畫列的所有測試與指令，結果逐條對應驗收標準記 `[證據 標準N]`。
- 有 UI 改動：有內建瀏覽器工具且 dev server 跑得起來就實際操作、記下操作與觀察；否則記「需使用者手動確認」。
- 與基準比較：新失敗一律算這次造成，除非能證明不是。
- 驗證完 `--set 狀態=待審查 --set "下一步=送 reviewer 審查"`。

## 階段 7：審查

- **低風險**：跳過，直接進階段 8。
- **中風險**：讀 `references/review.md`，呼叫 `doit:reviewer` subagent（背景執行），輸入只有：需求原文、計畫 vN、驗收標準、`git diff <起始SHA>..HEAD` 與工作目錄變更、專案路徑。**不給實作過程**。
- 結果以 `[審查 reviewer @<sha>] 結論：…` 加逐條意見記進任務檔。blocker / major 必須修（回階段 5 的對應步驟）；minor 可修可記。修完只重審改過的部分，最多兩輪，之後停下交使用者。
- **審查後的修正不做 wip commit**，留在工作目錄，等門檻通過後進交付 commit。這樣交付 commit 一定有內容，也不需要改寫已有的 commit。

## 階段 8：完成

完成門檻（全部成立）：每條驗收標準有證據；基準檢查沒有新失敗；審查沒有未處理的 blocker/major；範圍外清單已回報。

門檻過後，**分兩次呼叫**：先 `--set 狀態=完成 --set "下一步=無（已完成）"`，再做**交付 commit** `<type>: <摘要>`。不能用 `&&` 串在同一條指令，因為 hook 在整條指令執行前就依舊狀態判定，會連狀態更新一起擋下。

- 工作目錄有未 commit 的變更（審查修正、最後一步）→ 全部進交付 commit。
- 沒有任何未 commit 變更（審查無意見、每步都做了 wip）→ `git commit --allow-empty`，訊息同樣寫 `<type>: <摘要>`，內文註明「完成門檻通過；變更在前面的 wip 檢查點」。
- **不要**用 `git reset --soft` 改寫既有 wip commit。檢查點保留，squash 由使用者在 merge 時決定。

有 CI 設定（`.github/workflows/`、`.gitlab-ci.yml` 等）就開 PR，沒有就回報分支名稱讓使用者自己 merge。

## 階段 9：檢討

中風險每次做；低風險只在有 `[錯誤]` 時做。讀 `references/retro.md`，把任務檔裡每個 `[錯誤]` 變成一條預防規則，用 `log.js --lesson project|global` 搭配 heredoc 寫進對應教訓檔；教訓檔裡已有同一個坑時改用 `log.js --lesson-bump global G-001`（再犯）或加 `--hit`（踩到既有問題），不重建條目也不手改次數。全域檔在 `~/.doit/LESSONS.md`，在專案目錄外，不要直接 Write 或 Edit。

## 回報格式

每個階段結束用 3–5 行回報：做了什麼、證據、下一步、需要使用者決定的事。不要貼整份任務檔。
