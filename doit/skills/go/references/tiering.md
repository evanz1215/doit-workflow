# 風險分級

關卡數量由**出錯的代價**決定，不由工作量決定。

## 判定順序

1. 先看是否命中任一條**高風險條件**。命中就是高，寫明命中哪一條。
2. 沒命中，看是否符合**中風險條件**。
3. 都不是，才是低。

## 高風險條件（命中任一條即高）

| 條件 | 例子 |
|---|---|
| 改資料結構、schema、migration | 新增欄位、改型別、改索引、改序列化格式 |
| 改權限、認證、授權規則 | 新增角色檢查、改 token 驗證、改誰能看什麼 |
| 改對外介面 | HTTP API 的路徑／參數／回應、公開函式簽名、CLI 參數、事件或訊息格式 |
| 刪除或覆寫資料 | 任何 delete、truncate、覆寫檔案、清快取影響正確性 |

## 中風險條件

- 改動跨兩個以上檔案，或
- 改動任何**有其他呼叫者**的函式／方法／元件（呼叫者從階段 1 的影響範圍清單來）。

## 低風險

- 單檔、無其他呼叫者受影響、可用一個既有測試或一次執行證明。
- 例：修一個只在一處用到的 helper、改文案、補一個測試。

## 規則

- 等級與命中條件寫進任務檔，使用者批准計畫時看得到。
- 使用者可以**升級**，不能降級。agent 也不能自行降級。
- 實作中發現實際影響超出判定（原以為單檔結果要改呼叫者、原以為不動 schema 結果要加欄位），記 `[升級]`，`--set 等級=<新級>`，告知使用者，並補走新等級多出來的關卡。
- 不確定時取較高的那一級。

## 等級對應的關卡（v0.2）

| 階段 | 低 | 中 | 高 |
|---|---|---|---|
| 探索 | 輕量 | 完整（呼叫者、既有測試） | 同中，另列影響範圍清單 |
| 計畫 | 簡版：做法 + 驗收標準 + 驗證方式 | 完整 | 完整 + 送批准前過 plan-critic |
| 批准 | 必須（v0.3 無人看管模式才可免） | 必須 | 必須（請求附 plan-critic 結論） |
| 實作 | 主 context，可不做檢查點 | 每步檢查點 commit | 每步派 fresh implementer，主 context 核對後做檢查點 commit，每步回報 |
| 驗證 | 相關測試 | 相關測試 + UI 實測 | 全部測試 + UI 實測 |
| 審查 | 無 | reviewer | verifier（實跑）→ reviewer |
| 檢討 | 有錯誤時 | 必做 | 必做 |
