# UI 瀏覽器驗證

使用者看得到的改動（畫面、互動、文案、樣式、輸出格式），測試通過不等於畫面對。這份檔案講怎麼把「怎麼看到它」寫成可執行的驗收標準，以及階段 6 怎麼實際看。

## 什麼算 UI 改動

改到任何會被瀏覽器或視窗呈現的東西：頁面元件、模板、樣式、前端狀態、API 回應中會直接顯示的欄位、CLI 的輸出格式。只改後端內部邏輯而輸出不變的不算。

## 階段 3：怎麼寫 UI 類驗收標準

「怎麼證明」欄三項都要有，缺一項就不是可執行的標準：

```
| 2 | 價格顯示兩位小數 | 瀏覽器：http://localhost:3000/products → 點第一個商品 → 價格欄顯示「$1,234.50」 | 「顯示兩位小數」 |
```

1. **網址**：dev server 的頁面路徑。不知道 port 就寫「<dev server>/products」，階段 6 再補。
2. **操作**：到那個畫面要做的事，一步一個動作。
3. **預期畫面**：具體的文字或狀態（「顯示『已儲存』」「按鈕變灰」「列表有 3 筆」），不是「正常顯示」。

能力判斷在寫計畫時就做：

- 專案有 e2e 或元件測試（Playwright、Cypress、Testing Library）→ 優先寫成測試，瀏覽器實測當補充。
- 是 web 專案且找得到 dev server 指令 → 寫瀏覽器操作。
- 是桌面應用（WPF、Electron 主程序、原生 app）、需要真實帳號登入、或 dev server 依賴拿不到的服務 → 寫「需使用者手動確認：<畫面、操作、預期結果>」，並在批准請求裡明說這條要使用者自己看。

## 階段 6：怎麼驗

1. **找 dev server 指令**：`package.json` 的 `scripts`（dev / start / serve）、README、`Makefile`、`.claude/launch.json`。記下來源檔案。找不到就不要猜一個指令硬跑，記「需使用者手動確認」。
2. **起 server**：有 `preview_start` 工具就用它（沒有 `.claude/launch.json` 時先建一條設定）；沒有就用 Bash 背景執行並把輸出導到 scratchpad 的 log 檔。等到 log 出現 ready 字樣或 port 可連再往下。起不來（port 被占、缺環境變數、缺資料庫）→ 記下確切錯誤，標「需使用者手動確認」，不要花超過兩次嘗試去修環境。
3. **照驗收標準操作**：開網址、做標準寫的每個動作。**用 `read_page` 或 `get_page_text` 讀實際文字**來比對預期畫面，截圖只用來輔助看版面，不能單獨當證據。
4. **看 console**：`read_console_messages` 只看 error 層級。新出現的錯誤算這次造成，除非能證明基準就有。
5. **記證據**：
   ```
   [證據 標準2] 瀏覽器：http://localhost:3000/products → 點「Widget」→ 價格欄文字「$1,234.50」，console 無 error
   ```
   每條 UI 標準一行，寫實際讀到的文字，不寫「符合預期」。
6. **收尾**：自己起的 server 自己停（`preview_stop` 或結束背景行程）。新增的 `.claude/launch.json` 若原本不存在，刪掉，不留在工作目錄裡變成計畫外變更。

## 高風險

verifier 沒有瀏覽器工具，UI 類標準由主流程在階段 6 驗，verifier 會把那些標準標為「無法驗證（UI）」。所以高風險任務的 UI 證據要在送 verifier 前就記好，證據行要有實際讀到的文字，reviewer 與使用者看紀錄就能判斷。

## 不要做的事

- 不要用「我打開看過了，沒問題」當證據。
- 不要為了讓頁面跑起來改專案設定檔或 .env；環境問題記下來交使用者。
- 不要在驗證時順手修看到的其他畫面問題，記 `[範圍外]`。
