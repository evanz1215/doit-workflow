# 任務檔與計畫格式

## 任務檔結構

```
---
狀態: 探索中 | 待使用者 | 待批准 | 已批准 | 實作中 | 待審查 | 完成 | 中止
模式: brownfield
等級: 低 | 中 | 高
命中條件: <定成這一級的依據：高或中風險條件原文；低風險寫「無」>
類型: feat | fix | refactor | test | perf | docs | chore
計畫版本: 0
批准: 無 | v1「<使用者原話>」
分支: 尚未建立 | <分支名>
base: main
起始SHA: <sha>
下一步: <一句話，接續時第一件要做的事>
---

## 需求原文
<只放使用者真的說過的字，逐字>

## 基準檢查
<指令 | 來源檔案 | 結果>，一行一項

## 影響範圍
<被修改的函式／介面 → 所有呼叫者（檔案:行）>

## 紀錄
[時間] [標籤] ...

## 計畫 v1
（見下方格式；新版本追加在檔尾，不改舊版本）
```

頂端欄位與紀錄行**只能用 `log.js` 寫**（`log.js --help` 看用法）。「需求原文」「基準檢查」「影響範圍」的內容與 `## 計畫 vN` 小節直接用 Edit 寫：前三節填在對應標題下，計畫追加到檔尾。`.doit/` 不是敏感目錄，Edit 不會被擋。

## 計畫格式

```markdown
## 計畫 v1

### 做法
<兩三句：改哪裡、怎麼改、為什麼這樣改>

### 方案比較（只在有兩種以上合理做法時寫）
| 方案 | 做法 | 優點 | 缺點 | 影響範圍 |
|---|---|---|---|---|
推薦：<方案> ，理由：<連結到這個專案的實際情況>

### 需要你決定（會改變使用者看得到的行為的假設；沒有就省略這一節）
- <疑問> → 預設：<做法>；另一個選擇：<做法>；影響：<使用者會看到什麼差別>

### 假設（其餘非阻擋型疑問的預設）
- <疑問> → 預設：<做法>（已查證：<檔案:行 或 跑過的指令>）
- <疑問> → 預設：<做法>（未查證：<為什麼沒辦法查>）

### 未釐清（阻擋）（兩輪後仍未回答才有）
- <疑問>：選項 A / 選項 B（建議 A，因為…）

### 驗收標準
| # | 標準 | 怎麼證明 | 對應需求 |
|---|---|---|---|
| 1 | <可觀察的結果> | <測試名 / 指令 / 瀏覽器操作與預期畫面> | <需求原文中的字句> |

### 實作步驟
| 步 | 做什麼 | 改哪些檔案 | 這一步的驗證 | 對應標準 |
|---|---|---|---|---|
| 1 | ... | ... | <跑哪個測試或怎麼執行> | 1, 2 |

### 測試策略
<整體要新增／修改哪些測試；refactor 寫行為不變的安全網>

### 範圍外
- <碰到也不做的事>，理由
```

## 寫法規則

- **對應需求**欄只能放使用者真的寫過的字。推論寫成原文，使用者會以為是自己說的而不去檢查。
- **驗收標準**每條都要能被證明；「程式碼看起來正確」不算證明。
- **使用者看得到的行為改變**（畫面、互動、輸出格式）至少一條標準要寫「怎麼看到它」。
- **實作步驟**以「做完能證明」切，不以檔案切；每步只依賴前面的步驟；驗收標準每一條都要落在某一步的驗證裡。
- **假設要標查證狀態**：凡是描述既有程式行為的假設（「多餘的參數會報錯」「這個函式只有一個呼叫者」），寫之前先看程式碼或實際跑一次，標「已查證」並附位置。真的查不了才標「未查證」並寫原因。沒查就當成事實寫進計畫，實作會照錯的前提做。
- **需要你決定**：假設的預設會改變使用者看得到的行為（輸出格式、捨入方式、錯誤訊息、相容性）時，不要埋在假設清單裡，移到「需要你決定」一節，寫出另一個選擇與差別。它不是阻擋型疑問：使用者整體同意就採預設，但批准請求要把這一節放在最前面，讓使用者一眼看到。
- **低風險簡版**：只要「做法」「驗收標準」「實作步驟」三節；有假設或需要使用者決定的事時，照上面兩條加上對應的節。

## 紀錄行標籤

| 標籤 | 用途 |
|---|---|
| `[完成] 步驟 N：…` | 一個實作步驟做完 |
| `[證據 標準N] …` | 某條驗收標準被證明：寫指令與結果摘要 |
| `[紀錄] …` | 其他過程紀錄 |
| `[錯誤 來源：agent\|使用者\|環境 分類：需求\|實作\|工具\|環境\|流程] …` | 出錯；階段 9 檢討的素材 |
| `[審查 reviewer @<sha>] 結論：…` | 程式碼審查結果；逐條意見另起行 `[審查 reviewer] [blocker\|major\|minor] …` |
| `[審查 verifier @<sha>] 結論：…` | 高風險實跑驗證結果（階段 7，在 reviewer 前） |
| `[審查 plan-critic @vN] 結論：…` | 高風險計畫審查結果（階段 3，送批准前） |
| `[批准 vN] 「原話」` | 使用者批准 |
| `[升級] 低→中：原因` | 等級升級 |
| `[範圍外] …` | 實作中碰到但不做的事 |
| `[停止] …` | 中止或停下的原因 |

## 接續檢查

1. `log.js --show` 看狀態與下一步。
2. 分支：`git branch --show-current` 等於「分支」欄；「尚未建立」則應在 base 上。
3. 起始 SHA 是祖先：`git merge-base --is-ancestor <起始SHA> HEAD`。
4. 工作目錄：`git status --porcelain` 的內容要能對上最後幾行 `[完成]`／`[紀錄]`。
5. 不符就列差異問使用者，不自動修。
