# 審查與完成門檻

**所有審查（plan-critic、verifier、reviewer）的每一輪，包含重審，都是一次新的 Agent 呼叫、前景執行。** 不用 SendMessage 接續上一輪的審查者：接續會變成背景執行，而且上一輪的脈絡會影響這一輪的獨立判斷。

## 呼叫 plan-critic（高風險，階段 3 送批准前）

用 Agent 工具呼叫 `doit:plan-critic`，前景執行。此時狀態還是「探索中」，不用改。

prompt 只包含以下內容，**不包含你的探索過程與推理**：

```
專案路徑：<絕對路徑>
base：<分支>　起始 SHA：<sha>
等級：高　命中條件：<原文>

## 需求原文
<逐字>

## 計畫 v<N>
<任務檔裡 ## 計畫 vN 的全文：做法、方案比較、假設、驗收標準表、實作步驟表、測試策略、範圍外>

## 影響範圍
<任務檔 ## 影響範圍 的內容>

## 專案慣例
<階段 0 整理的相關規則，逐條>

請以繁體中文回覆，依你的輸出格式給結論與逐條意見。
```

結果處理：

- 寫進任務檔：`[審查 plan-critic @v<N>] 結論：可送批准 | 需修改`，再逐條 `[審查 plan-critic] [blocker|major|minor] <意見> → <處理：已修改：怎麼改 | 不採納：理由 | 記下>`。
- blocker / major 必須改。使用者還沒看過計畫，所以**直接改 `## 計畫 v<N>` 本身**，不開新版本；改完記 `[紀錄] 依 plan-critic 修改計畫 v<N>：<改了什麼>`。plan-critic 說漏列呼叫者而且會讓等級變動的，照 `tiering.md` 處理（只升不降）。
- 重送時**呼叫一個新的 `doit:plan-critic`，前景執行**，不要用 SendMessage 接續上一個（接續的 subagent 會在背景跑，主流程會在結果回來前就結束回合，使用者看到的是停在半路）。prompt 用上面的模板，再加一行「只看以下修改過的部分：<列出改過的節>」，附修改後的那幾節全文。
- 最多兩輪。兩輪後仍有 blocker / major，照常送批准，但批准請求裡要逐條列出未解決意見與你的理由，讓使用者決定。
- 不採納的理由要具體到這個專案（例如「此 API 只有內部一個呼叫者，見影響範圍」），不能只寫「不需要」。

## 呼叫 verifier（高風險，階段 7，在 reviewer 之前）

用 Agent 工具呼叫 `doit:verifier`，前景執行。狀態已是「待審查」。

prompt 只包含以下內容，**不包含實作過程、不包含任務檔裡已記的證據**（verifier 要自己跑，不是看你跑過）：

```
專案路徑：<絕對路徑>
分支：<分支名>　起始 SHA：<sha>
暫存目錄：<這個 session 的 scratchpad 路徑或 os tmpdir 下一個新目錄>（放你的暫時測試腳本，不要寫進專案）

## 需求原文
<逐字>

## 假設
<計畫的假設節，逐條>

## 驗收標準
<計畫的驗收標準表全文，含「怎麼證明」欄>

## 基準檢查
<任務檔 ## 基準檢查 的內容：指令、來源、當時結果>

## 變更
請自行執行：git -C <專案路徑> diff <起始SHA>  （含工作目錄未 commit 的變更）

請以繁體中文回覆，依你的輸出格式逐條實跑並給結論。
```

結果處理：

- 寫進任務檔：`[審查 verifier @<目前 HEAD 短 sha>] 結論：通過 | 未通過`，再逐條 `[審查 verifier] [blocker|major|minor] <意見> → <處理>`。verifier 標「無法驗證（UI）」的標準，確認任務檔已有主流程記的瀏覽器證據（見 `ui-verify.md`）；沒有就先補。
- 未通過或有 blocker：回階段 5 對應步驟修，修完重送 verifier，prompt 寫「只重跑以下標準：<編號>」。最多兩輪。
- verifier 回「通過」後才呼叫 reviewer。reviewer 的 prompt 可在「## 變更」後加一行「verifier 結論：通過（<日期>）」，不附 verifier 的過程。
- 兩輪後仍未通過：`--set 狀態=待使用者 --set "下一步=使用者決定如何處理 verifier 意見"`，停下。

## 呼叫 reviewer（中風險與高風險）

用 Agent 工具呼叫 `doit:reviewer`，**前景執行**（等它回來再往下，不用背景加輪詢）。階段 6 結尾已設 `狀態=待審查` 與對應等級的「下一步」，這裡不用再設。

prompt 只包含以下內容，**不包含實作過程、不包含你的推理**：

```
專案路徑：<絕對路徑>
起始 SHA：<sha>
分支：<分支名>

## 需求原文
<逐字>

## 計畫 v<N>
<做法、假設（非阻擋型疑問的預設）、驗收標準表、實作步驟表、範圍外>

## 變更
請自行執行：git -C <專案路徑> diff <起始SHA>  （含工作目錄未 commit 的變更）

## 專案慣例
<階段 0 整理的相關規則，逐條>

請以繁體中文回覆，依你的輸出格式給結論與逐條意見。
```

「假設」要給：reviewer 才知道哪些行為（例如非數字輸入不處理）是計畫預設而不是漏做。不要在 prompt 裡附「工作目錄乾淨」「每步都有 wip」這類過程描述。

## 審查結果處理

reviewer 回傳的每條意見分 blocker / major / minor。

- 寫進任務檔：先一行 `[審查 reviewer @<目前 HEAD 短 sha>] 結論：可合併 | 需修正`，再逐條 `[審查 reviewer] [blocker|major|minor] <意見> → <處理：已修正：怎麼改 | 不採納：理由 | 記下>`。
- **blocker / major 必須修**，回階段 5 對應的步驟，修完重跑該步驗證，再送審**只重審改過的部分**（prompt 寫明「只看自上次審查後的 diff：git diff <上次審查 sha>」）。
- **審查後的修正不做 wip commit**，留在工作目錄等交付 commit 一起進去；重審時 prompt 寫「含工作目錄未 commit 的變更」。
- 最多兩輪。兩輪後仍有 blocker / major，`--set 狀態=待使用者 --set "下一步=使用者決定如何處理審查意見"` 停下，把未解決意見列給使用者。
- minor 可修可記；不修的要寫理由。
- 不採納 reviewer 意見時，理由要具體到這個專案，不能只寫「不需要」。

## 完成門檻（全部成立才能把狀態改成「完成」）

| # | 條件 | 怎麼確認 |
|---|---|---|
| 1 | 每條驗收標準都有 `[證據 標準N]` | 對照計畫的驗收標準表逐條數 |
| 2 | 基準檢查沒有新失敗 | 重跑 `## 基準檢查` 列的指令，比對結果 |
| 3 | 審查沒有未處理的 blocker / major（低風險無此項；中風險看 reviewer；高風險 verifier 與 reviewer 兩者都要） | 看最後一組 `[審查 reviewer]`（高風險加 `[審查 verifier]`）行 |
| 4 | 工作目錄沒有計畫沒提到的檔案變更 | `git status --porcelain` 與 `git diff --stat <起始SHA>` 逐檔對照實作步驟表 |

門檻過了：`--set 狀態=完成 --set "下一步=無（已完成）"` → 依設定交付（見 SKILL.md 階段 8）：`commit=on` 做交付 commit（有未 commit 變更就含進去；沒有就 `--allow-empty`；不改寫既有 wip），`commit=off` 不 commit、列出變更檔案 → `pr=on` 才 push 並開 PR，否則回報分支名。

交付回報必須逐條列出任務檔所有 `[範圍外]` 行與計畫「範圍外」節的項目，使用者才知道什麼沒做。這是回報的義務，不是改狀態前的門檻（回報發生在門檻之後，不可能先成立）。

門檻沒過：不得改狀態、不得做交付 commit（hook 也會擋）。缺什麼補什麼，補不了就 `--set 狀態=待使用者` 說明。
