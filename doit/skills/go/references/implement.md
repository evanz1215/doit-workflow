# 高風險每步派 fresh implementer

只有**高風險**任務用。低／中風險在主 context 實作，不讀這份。

為什麼：主 context 走到實作時已經累積了探索、釐清與計畫的來回，容易照著自己先前的印象寫而不是照計畫寫。每步交給一個只看得到「這一步」的實作者，做出來的東西只能來自計畫本身；計畫寫得不夠清楚也會在這裡暴露。

## 分工

四拍的順序不變，只是前兩拍換人做：

| 拍 | 誰做 |
|---|---|
| 1 改這一步列的檔案 | implementer |
| 2 跑這一步的驗證 | implementer，主 context 核對時再跑一次 |
| 3 記 `[完成]`、`[證據]`、更新「下一步」 | 主 context |
| 4 `wip:` 檢查點 commit（設定 `commit=off` 時略過） | 主 context |

implementer 不 commit、不寫任務檔。紀錄與 commit 的順序仍由主 context 掌握，接續時才對得上。

## 呼叫 implementer

每一步用 Agent 工具呼叫一次 `doit:implementer`，**前景執行**，一次只派一個（步驟有先後依賴，不平行）。每步都是新的呼叫，不要用 SendMessage 接續上一步的 implementer。

派之前先 `--set "下一步=步驟 N：等 implementer 回報後核對"`，中斷時才知道停在哪。

prompt 只包含以下內容，**不包含對話、探索過程、你的推理、其他步驟的細節**：

```
專案路徑：<絕對路徑>
分支：<分支名>

## 這一步（步驟 N）
做什麼：<實作步驟表該列的「做什麼」>
改哪些檔案：<該列的「改哪些檔案」，逐一列出>
這一步的驗證：<該列的「這一步的驗證」>

## 對應的驗收標準
<驗收標準表中這一步對應的列，含「怎麼證明」>

## 相關假設
<計畫假設節中與這一步有關的條目；沒有寫「無」>

## 已定的決定
<計畫「需要你決定」一節中與這一步有關的項目，寫最後採用的做法（預設，或使用者改選的那個）；沒有寫「無」>

## 前面步驟的產出
<步驟 1..N-1 各一行：新增或改了什麼可以依賴的函式／檔案／介面；第一步寫「無」>

## 範圍外
<計畫的範圍外節>

## 專案慣例
<階段 0 整理的相關規則，逐條>

請以繁體中文回覆，依你的輸出格式回報。
```

「前面步驟的產出」只寫結果（例如「`src/page.js` 匯出 `parsePage(str)`，回傳 `{page, size}`，非法輸入丟 `RangeError`」），不寫怎麼做出來的。

## 核對（主 context，implementer 回「待核對」之後）

不直接相信回報，自己看三件事：

1. **範圍**：`git status --porcelain` 列出的檔案都在這一步的「改哪些檔案」裡。多出來的檔案不是你派的，先看內容：屬於這一步必要的小偏差就記 `[紀錄]`；否則還原那個檔案並記 `[錯誤 來源：agent 分類：實作]`。
2. **驗證**：自己再跑一次這一步的驗證指令，看到通過。implementer 說過了但你跑不過，以你跑的為準。
3. **測試有效**：這一步新增或修改的測試，斷言比對的是具體值。

三件都成立才進第 3 拍記 `[完成] 步驟 N：…` 與 `[證據 標準N] …`（證據寫你自己跑的指令與結果），再做第 4 拍 wip commit。implementer 回報的「範圍外發現」逐條記 `[範圍外]`；「偏離計畫」是小偏差就記 `[紀錄]`，動到做法、範圍或資料結構的照階段 5 的規則停下重提計畫。

核對完、第 3、4 拍做完之後，依 SKILL.md「階段回報」的格式回報這一步（標題「🔨 Step 5 實作：步驟 N／總步數 …」，「完成」欄加 implementer 回報的狀態與你的核對結果），不等回覆就繼續。

## 沒過的處理

| 情況 | 做法 |
|---|---|
| 回「失敗」，或你核對時驗證不過 | 記 `[錯誤 來源：agent 分類：實作]`。**派一個新的 implementer**，prompt 多一節 `## 上一次的結果`：工作目錄保留了上次的修改、驗證指令、失敗輸出的關鍵幾行。不附上一個 implementer 的推理。 |
| 回「受阻：要動清單外的檔案」 | 該檔案沒有其他呼叫者且不改變等級：記 `[紀錄]`，把檔案加進這一步的清單後重派。否則是計畫漏了，回階段 3 重提計畫。 |
| 回「受阻：做法行不通／缺資訊」 | 能從程式碼查到答案就補進 prompt 重派；查不到或要換做法，回階段 3 或 `--set 狀態=待使用者`。 |

同一步的失敗次數沿用階段 5 的上限：implementer 回報的「失敗」與你核對不過各算一次，累計 3 次就停，記 `[錯誤]`，回報使用者。重派不重設計數。

**不要自己接手改**。主 context 下場修，等於把 fresh 的隔離拿掉；要修就再派一個。唯一例外是還原計畫外的檔案。

## 審查後的修正（階段 7 回來）

verifier 或 reviewer 的意見決定要修時，**同樣派一個新的 implementer，主流程不自己改**。理由和實作步驟一樣：你剛讀完審查者的整份回報與自己的處理判斷，下場改就把隔離拿掉了。

- **prompt 用上面的模板**，三處照下面寫，其餘各節照舊：
  - `## 這一步（修審查意見）`：
    - 做什麼：修掉下面這條審查意見。貼意見原文：位置（檔案:行）、問題、重現指令或輸入、預期與實際。只貼要修的這一條，不附審查者的結論與其他意見。
    - 改哪些檔案：意見指到的檔案與它對應的測試檔。這些檔案都要是計畫實作步驟表列過的；要動到表外的檔案代表計畫漏了，照「沒過的處理」的「受阻：要動清單外的檔案」處理。
    - 這一步的驗證：意見的重現指令不再出錯，加上那個檔案所屬步驟原本的驗證指令。
  - `## 前面步驟的產出`：寫「全部步驟已完成」與這次修正會依賴的函式／介面。
- **核對**照「核對」三件事做。過了在任務檔那條意見的紀錄行寫 `→ 已修正：<怎麼改>`，並補一行 `[證據 標準N]`（修正影響到的標準，寫你自己重跑的指令與結果）。
- **不做 wip commit**：審查後的修正留在工作目錄，等完成門檻通過後進交付 commit（`commit=off` 時本來就不 commit）。
- **幾條意見改同一批檔案**可以併成一次派工，prompt 裡逐條列；互不相干的分開派，一次一個。
- **失敗計數另起**：同一條意見派了 3 次仍核對不過就停，`--set 狀態=待使用者 --set "下一步=使用者決定如何處理審查意見"`。
- **minor** 決定要修時也走這條路；不值得為它派一次就記下不修並寫理由，列在交付回報。
- 修完依 `review.md` 的規則重審：verifier 的意見而且動到測試以外的程式碼就重送 verifier，reviewer 的意見就重送 reviewer 只看改過的部分。

低／中風險沒有 implementer，審查修正由主流程自己改。

## 接續

中斷在 implementer 執行中或核對前：工作目錄會有這一步的未 commit 修改，任務檔沒有對應的 `[完成]`。這是正常現象。

- 未 commit 的檔案都在這一步的清單內 → 從「核對」開始：跑驗證，過了就補第 3、4 拍；不過就照「沒過的處理」派新的 implementer，`## 上一次的結果` 寫「上次中斷，工作目錄保留了部分修改」。
- 有清單外的檔案 → 照 SKILL.md「接續」的規則問使用者。

## 等級在實作中升到高

`[升級]` 之後還沒做的步驟改用 implementer；已經做完並有 wip commit 的步驟不重做。
