# doit：依風險分級的開發工作流（v0.2）

把開發指令變成一次有證據、可回退、可接續的交付。

**語言**：所有回報、計畫、任務檔紀錄、commit 訊息一律繁體中文（程式碼與指令除外）。

**v0.2 範圍**：低／中／高風險、brownfield、一般模式。高風險多四道關卡：計畫送批准前先過 `doit:plan-critic`、實作每步派一個 fresh `doit:implementer`、審查時先 `doit:verifier` 實跑再 `doit:reviewer`、有 UI 改動時依 `references/ui-verify.md` 用內建瀏覽器實測。`auto`、`new` 子指令尚未實作，收到時告知並改走一般模式。

指令：$ARGUMENTS

## 分派

| `$ARGUMENTS` | 做什麼 |
|---|---|
| 空白 或 `resume` | 走「接續」；沒有進行中任務時請使用者說明要做什麼 |
| `status` / `abort` | 照 `${CLAUDE_PLUGIN_ROOT}/skills/status/SKILL.md` / `${CLAUDE_PLUGIN_ROOT}/skills/abort/SKILL.md` 做（Read 被擋就用 `log.js --ref status`／`--ref abort`），並告訴使用者之後可以直接用 `/doit:status`、`/doit:abort` |
| `auto ...` / `new ...` | 告知尚未支援（v0.3、v0.4 才有），詢問是否以一般模式繼續 |
| 其他 | 新任務，從階段 0 開始 |

## 三條硬規則（hooks 會強制，skill 只是說明）

1. **未批准不動手**：任務狀態在「已批准」之前，Edit/Write 專案檔案會被 hook 擋下。
2. **未達門檻不交付**：完成門檻（`references/review.md`）沒過，狀態不是「完成」時，非 `wip:` 前綴的 `git commit` 與任何 `git push`/`merge` 都會被擋下。
3. **離開前存狀態**：有進行中任務時，「下一步」欄位是空的就無法結束回合。

## 任務檔與寫入工具

- 任務檔在 `.doit/tasks/<日期>-<slug>.md`，`.doit/ACTIVE` 指向它。不進 git。`.doit/` 不是敏感目錄，Edit/Write 不會被擋。
- **頂端欄位與紀錄行一律用 log.js 寫**（有格式驗證、自動時間戳、自動插到「## 紀錄」小節）。
- **其餘小節直接用 Edit 寫**：填「需求原文」「基準檢查」「影響範圍」三節的內容，以及在檔尾追加 `## 計畫 vN`。不要用 node -e、`cat >>` heredoc 或其他 shell 腳本改任務檔：長段含反引號與表格的 Markdown 會被 Bash 工具的解析器拒跑。
- 不確定用法時 `node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --help`。
- 紀錄行文字含 `$`（金額、變數名）時用**單引號**包整個參數；雙引號裡的 `$20.00` 會被 Bash 工具當成變數擋下。

```bash
node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --new <slug> --set 類型=feat
node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --set 狀態=待批准 --set "下一步=等使用者批准計畫 v1"
node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" "[完成] 步驟 1：新增 parsePage()" "[證據 標準2] npm test -- pagination 通過"
node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --show
```

標籤：`[完成]` `[紀錄]` `[證據 標準N]` `[錯誤 來源：agent|使用者|環境 分類：需求|實作|工具|環境|流程]` `[審查 reviewer|verifier @<sha>]` `[審查 plan-critic @vN]` `[批准 vN]` `[升級]` `[停止]` `[範圍外]`。格式見 `references/plan-format.md`。

## 參考檔（到該階段再讀）

| 檔案 | 何時讀 |
|---|---|
| `${CLAUDE_PLUGIN_ROOT}/skills/go/references/tiering.md` | 階段 2 初判、階段 3 定級、實作中懷疑要升級時 |
| `${CLAUDE_PLUGIN_ROOT}/skills/go/references/plan-format.md` | 階段 3 寫計畫前；接續時 |
| `${CLAUDE_PLUGIN_ROOT}/skills/go/references/implement.md` | 階段 5 高風險開始實作前；高風險任務接續在「實作中」時 |
| `${CLAUDE_PLUGIN_ROOT}/skills/go/references/review.md` | 階段 3 高風險送 plan-critic 前；階段 7 審查；階段 8 完成門檻 |
| `${CLAUDE_PLUGIN_ROOT}/skills/go/references/ui-verify.md` | 階段 3 寫 UI 類驗收標準時；階段 6 有 UI 改動要驗證時 |
| `${CLAUDE_PLUGIN_ROOT}/skills/go/references/retro.md` | 階段 9 檢討 |

**參考檔讀不到時**：plugin 目錄常不在 session 的允許目錄內，Read 會被權限擋下（訊息含「haven't granted」「requested permissions」）。

- 改用 `node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --ref <名稱>` 印出同一份內容，名稱是檔名去掉 `.md`（`--ref tiering`、`--ref plan-format`、`--ref implement`、`--ref review`、`--ref ui-verify`、`--ref retro`）。其他 skill 的 SKILL.md 也一樣，用目錄名（`--ref status`、`--ref abort`）。不要改用 `cat` 或其他工具繞。
- **兩種方式都讀不到就停下**：`--set 狀態=待使用者 --set "下一步=使用者放行參考檔的讀取權限"`，回報讀不到哪一份、需要的權限（Read plugin 目錄，或允許 `Bash(node:*)`）。**不得憑印象或這份 SKILL.md 的摘要繼續**：計畫格式、審查 prompt 模板、完成門檻的細節只寫在參考檔裡，少了它們做出來的東西會走樣而且沒人發現。

## 階段回報

**每個階段結束都要回報一次，再繼續下一階段。** 使用者靠這些回報知道走到哪、結果如何、有沒有出問題。回報不是確認點：除了階段 2 有阻擋型疑問、階段 4 等批准、以及停下交給使用者的情況，回報完就直接往下做，不等回覆。

- **回報要寫成給使用者看的文字輸出**，不能只寫在思考裡。思考區塊使用者看不到，寫在那裡等於沒回報。
- **headless（`claude -p`）也一樣要回報**，即使當下沒人在看：事後稽核靠的就是這些回報。
- **先回報，再動下一個階段**：這個階段的回報輸出之後，才可以呼叫下一個階段的第一個工具。不要一路做到要停下時才一次補前面的回報。

格式固定如下，直接輸出 Markdown，不包在程式碼區塊裡：

```markdown
### {emoji} Step {N} {階段名稱}：{這個階段的結論}

進度 {已完成的階段數}／10：✅ 前置 ✅ 探索 ▶ 釐清 ⬜ 計畫 ⬜ 批准 ⬜ 實作 ⬜ 驗證 ⬜ 審查 ⬜ 完成 ⬜ 檢討

- **完成**：這個階段實際做出了什麼（結果，不是過程）
- **證據**：指令與結果、檔案位置；沒有就省略這一欄
- **問題**：遇到什麼、怎麼處理、還沒解決的；沒有寫「無」
- **下一步**：接下來的階段與具體動作
- **需要你處理**：要使用者回答或決定的事；不需要寫「無，自動繼續」
```

| 階段 | emoji | 「完成」欄必須包含 |
|---|---|---|
| 0 前置檢查 | 🧰 | 基準檢查結果（幾過幾敗）、找到的檢查指令與來源檔、採用的教訓條目 |
| 1 探索 | 🔍 | 要改的函式／介面、所有呼叫者（檔案:行）、相關測試 |
| 2 釐清 | ❓ | 問了哪些問題（附建議答案）；沒有就寫「無阻擋型疑問」 |
| 3 計畫 | 📝 | 等級與命中條件、步驟數、驗收標準數；高風險加 plan-critic 結論 |
| 4 批准 | ✋ | 批准請求（見下） |
| 5 實作 | 🔨 | **每一步回報一次**：標題寫「步驟 N／總步數」，列改了哪些檔案；「證據」欄直接寫這一步的驗證指令與結果（例如「npm test 10 過 0 敗」），不要寫「見下一份回報」；高風險加 implementer 回報狀態與你的核對結果 |
| 6 驗證 | 🧪 | 逐條驗收標準：通過／失敗／未驗證，各附一行證據；基準比對結果 |
| 7 審查 | 👀 | 各審查者的結論、blocker／major 的處理；低風險寫「低風險，跳過」。只寫審查本身，完成門檻檢查是 Step 8 的事 |
| 8 完成 | 📦 | 完成門檻四項各自的檢查結果，加上交付回報（見下） |
| 9 檢討 | 🪞 | 新增或累加的教訓條數與編號；不需要檢討時寫原因 |

- **進度清單**：每份回報的標題下一行固定放這一行，十個階段依序列出，讓使用者不用往上捲就知道走到哪。
  - ✅ 已完成的階段（包含正在回報的這一個）；▶ 接下來要做的階段；⬜ 還沒到的階段；⏭ 跳過的階段（例如低風險的審查）；❌ 停下或失敗的階段。
  - 實作階段還有步驟沒做完時寫「▶ 實作 2／3」，表示三步裡做完兩步；整個階段做完才換成 ✅。
  - 「等你批准」那份回報：批准還沒完成，寫「▶ 批准」，前面的數字不含批准。
  - 上面模板那一行是「釐清」之前的樣子，只是示意；每次照實際狀態重寫，不要照抄。
  - 環境有內建的待辦清單工具（TodoWrite，或 TaskCreate／TaskUpdate）時，在階段 0 一開始建立同樣的十個項目，每完成一個階段更新一次；沒有這個工具就只用這一行，不要為此呼叫別的工具。
- **結論**寫在標題冒號後面，例如「🧪 Step 6 驗證：6／7 通過，標準 3 失敗」。失敗或停下時在結論前加 ❌，有未解決的問題加 ⚠️；✅ ❌ ⚠️ 只表示狀態，不當階段 emoji 用。
- **跳過的階段也要回報**，標題寫明跳過，例如「👀 Step 7 審查：低風險，跳過」，使用者才不會以為漏做。內容照樣用模板的五欄（沒有證據就省略「證據」欄），不要改用自由條列。
- **停下或回到前面的階段**時立刻回報，標題寫實際狀態，例如「❌ 🔨 Step 5 實作：步驟 2 驗證連續失敗 3 次，停下」。
- **每欄一兩行**，詳細證據留在任務檔，不要貼整份任務檔或整份 diff。「下一步」要跟 `log.js` 設的「下一步」欄一致。
- **emoji 只用在對話回報**，不要寫進任務檔或 `log.js` 的紀錄行。
- 兩個可以長一點的例外：
  - **批准請求**（Step 4）：使用者不開任務檔就能判斷。「需要你決定」的項目放最前面（每項寫預設、另一個選擇、差別）；接著是定級與命中條件、做法、步驟、驗收標準、其餘假設的預設（未查證的要標出來）、範圍外、完成後會不會 commit／開 PR；高風險加 plan-critic 結論、採納與不採納的理由。
  - **交付回報**（Step 8）：做了什麼；**每條驗收標準一行**（編號、通過／失敗、證據摘要），不能只寫「全部通過」，讓使用者不用往回翻 Step 6；完成門檻四項的結果；沒採納的 major 審查意見逐條列出並附理由；分支與 commit；採用的假設；所有 `[範圍外]`；需要使用者接手的事（merge、PR）。

## Bash 指令寫法

Claude Code 會在執行前靜態檢查 Bash 指令，複合指令常被擋下要求核准。為了少被擋：

- **一次呼叫只跑一條指令**。不用 `;`、`&&`、`||` 串接；需要多條就分成多次呼叫。
- 不用 `$?`、`$(...)`、反引號取值；需要結束碼時直接看工具回報的 exit code。
- `log.js` 的紀錄行或 heredoc 內文裡，不要讓半形 `=` 緊接在空白或反引號後面（例如寫 CLI 的等號旗標時），會被當成 zsh 展開擋下；改寫成文字描述或全形「＝」。
- 被擋下時改寫成單一指令再試一次，不要換成別的工具繞過。

## 接續

1. `log.js --show`。狀態是「完成」或「中止」就當作沒有進行中任務。再跑 `log.js --config` 重新讀設定（使用者可能在中斷期間改過）。
2. 檢查：目前分支等於「分支」欄（「尚未建立」則應在 base 上）；「起始SHA」是 HEAD 的祖先（`git merge-base --is-ancestor <sha> HEAD`）；工作目錄狀態與最後幾行紀錄相符。
   - **差異能用計畫解釋就繼續**：未 commit 的檔案正好是「下一步」那一步「改哪些檔案」欄的檔案、或紀錄說要做的 wip commit 已存在，這是中斷在四拍之間的正常現象。`commit=off` 時沒有 wip commit，只對照紀錄與工作目錄：已記 `[完成]` 的步驟，它的檔案修改應該都還在工作目錄。記一行 `[紀錄] 接續核對：…` 說明判斷，從對應的那一拍繼續（通常是第 2 拍：驗證）。
   - **其他差異問使用者**：改到計畫外的檔案、分支不對、起始 SHA 不是祖先、紀錄說已 commit 但 git log 沒有。列出差異，`--set 狀態=待使用者`，不自動修。
   - 接續時順便重讀一次上一步新增或修改的測試檔，確認斷言真的比對具體值，不是 `assert.ok` 這類永遠通過的寫法。
3. 依「狀態」與「下一步」繼續。**狀態「待批准」時重新提交計畫等批准，不能直接開工**；「待使用者」且計畫版本 0 時重新列出未回答的釐清問題。

## 階段 0：前置檢查

- 必須是 git repo。不是就告知並停止（建議 `git init` 後 commit 一次再來）。
- `git status --porcelain` 必須為空（`.doit/` 已排除）。不乾淨就請使用者自己 commit 或 stash，不要替使用者決定。
- 記下 **base 分支**與**起始 SHA**（`git rev-parse HEAD`）。之後「完整變更」一律以起始 SHA 為基準。
- 讀 `CLAUDE.md`、`AGENTS.md`、`README.md`、`CONTRIBUTING.md`（有哪個讀哪個），整理與這次任務相關的慣例與禁止事項。
- 從 `package.json` / `pyproject.toml` / `Makefile` / `go.mod` / CI 設定找測試、lint、型別檢查、build 指令，**記下來源檔案**。找不到的不猜，列為「無基準」並在計畫中標明。
- **執行任何指令前先看副作用**：會寫 DB、打外部服務、寄信、刪資料的，只在確認目標是本機或測試環境時才跑；無法確認就不跑，記為未驗證。
- 跑一次基準檢查（lint + 相關測試；夠快就全跑），結果寫進任務檔 `## 基準檢查`。
- **基準指令被工具權限擋下**（訊息含「requires approval」「can't be checked」「was blocked」）：這不是指令錯，是 Claude Code 的安全檢查。先試一次改寫：單一指令、不串接、可執行檔與路徑都寫絕對路徑字面值、不用變數、輸出用 `> log 2>&1` 導到 scratchpad。還是被擋就在 `## 基準檢查` 記「被權限擋下：<確切指令>」，並在給使用者的回報裡列出這條指令與需要的權限（例如 `Bash(msbuild:*)`），請使用者放行後重跑或接受無基準。**不要**自行改走替代方案（自建 harness、改用別的建置工具）來取代基準，替代方案只能是額外證據。
- 讀設定：`node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --config`，記下 `commit` 與 `pr`（沒有設定檔時是預設值 commit=on、pr=off）。階段 5 的檢查點與階段 8 的交付都照它做，批准請求裡要寫明。
- 讀教訓檔：`node "${CLAUDE_PLUGIN_ROOT}/tools/log.js" --lessons` 會印出專案（`.doit/LESSONS.md`）與全域（`~/.doit/LESSONS.md`）兩份；全域檔在專案目錄外，不要用 cat 或 Read 直接讀。挑相關條目照做。
- **指令提到計畫檔**（例如「依 `.doit/plans/<檔名>` 的 T2：…」，由 `/doit:plan` 產生）：先讀那份計畫檔。
  - 該任務的目標、範圍、驗收重點，以及它引用的決定與假設，當成需求的一部分。計畫檔「範圍外」列的事這個任務也不做。
  - 依賴的任務狀態不是「完成」：告知使用者哪個任務要先做，停下，不建立任務檔。
  - 計畫檔的預估等級只是預估。照階段 3 自己定級；你的判斷比預估低時取預估那一級。
  - 計畫檔裡標「未查證」的假設，輪到這個任務用到時要查證。
- 建立任務檔：`log.js --new <slug> --set 類型=<type> --set base=<分支> --set 起始SHA=<sha> --set "下一步=探索"`。類型：feat / fix / refactor / test / perf / docs / chore。任務來自計畫檔時，建立後用 Edit 把計畫檔任務清單裡該任務的狀態改成「進行中」（頂端狀態還是「草稿」或「已確認」的也改成「進行中」），並在任務檔「需求原文」下一行註明「來源：<計畫檔路徑> T<N>」。
- **回報**：依「階段回報」回報「🧰 Step 0 前置檢查：…」，接著進階段 1。

## 階段 1：探索（只讀不改）

- 讀相關程式碼、類似的既有實作、相關測試。範圍大時用 Explore subagent 平行搜。
- 找出被修改函式／介面的**所有呼叫者**，寫進任務檔 `## 影響範圍`。這是分級依據。
- 使用既有函式前看實際回傳值與錯誤路徑，不憑名稱猜。
- 查外部文件前先看 lock 檔確認實際安裝版本。
- 探索中發現階段 0 沒跑到的相關測試，**改任何程式碼之前**補跑，追加到基準。
- **回報**：依「階段回報」回報「🔍 Step 1 探索：…」，接著進階段 2。

## 階段 2：釐清需求

疑問分兩類：

- **阻擋型**：答案若與猜測相反，計畫要重寫一半以上（做法、範圍、資料結構、對外行為）。**寫計畫前就問**。
- **非阻擋型**：只影響細節、有合理預設。寫進計畫「假設」欄附預設做法。

以下一律算阻擋型：刪除／覆寫／清除資料時是軟刪還是硬刪；新增權限規則時誰可以做。

規則：能從程式碼、文件、git log 查到的自己查；一次問完（最多 5 題）、每題附建議答案與理由；停下前 `--set 狀態=待使用者 --set "下一步=等釐清回答"`；最多兩輪，之後列為「未釐清（阻擋）」，批准時使用者必須逐項選。沒有阻擋型疑問就直接往下，不硬湊。
- **回報**：依「階段回報」回報「❓ Step 2 釐清：…」。有阻擋型疑問時，這份回報就是提問，停下等回答；沒有就寫「無阻擋型疑問」並直接進階段 3。

## 階段 3：計畫落檔

先讀 `references/tiering.md` 定級、`references/plan-format.md` 看格式，然後把 `## 計畫 v1` 追加到任務檔尾端。

- **方案比較**：有兩種以上合理做法、且選擇影響結構／資料格式／相容性／效能時才寫，2–3 個選項，推薦一個並連結到這個專案的實際情況。只有一種合理做法就不比較。
- **驗收標準**：每條要能被測試或實際執行證明，並寫明怎麼證明。使用者看得到的行為改變至少一條要寫「怎麼看到它」（既有 e2e／元件測試 → 瀏覽器實際操作 → 都沒有就寫「需使用者手動確認：頁面、操作、預期結果」）。瀏覽器操作類的標準照 `references/ui-verify.md` 的寫法：網址、操作、預期畫面三項都要有。
- **實作步驟**：以「做完能用一個測試或一次執行證明」為單位，最多 5 步，每步只依賴前面的步驟。低風險的單檔改動可以只有 1 步；中風險以上至少 2 步，讓檢查點有意義。驗收標準每一條都要落在某一步的驗證裡。
- **假設**：描述既有程式行為的假設，寫之前先看程式碼或實際跑一次，標「已查證」附位置；查不了才標「未查證」附原因。預設做法會改變使用者看得到的行為的，移到「需要你決定」一節（寫法見 `references/plan-format.md`）。
- **範圍外**：實作時碰到只能記 `[範圍外]`，不能順手做。
- **需求原文**只放使用者真的說過的字。
- 定級後 `--set 等級=<級> --set 命中條件=<條件或無> --set 計畫版本=1`。低／中風險接著 `--set 狀態=待批准 --set "下一步=等使用者批准計畫 v1"` 送批准。
- **高風險：送批准前先過 plan-critic**。讀 `references/review.md` 的「呼叫 plan-critic」，呼叫 `doit:plan-critic` subagent（前景執行），輸入只有需求原文、等級與命中條件、計畫全文、影響範圍、專案路徑與慣例，**不給你的推理**。計畫全文與影響範圍要**貼進 prompt**，不要給任務檔路徑叫它自己讀（任務檔的紀錄節有你的處理說明，審查者讀到就不獨立）。結果以 `[審查 plan-critic @v1] 結論：…` 加逐條意見記進任務檔。blocker 必須改；major 預設要改，不採納要有連結到這個專案的具體理由，並列在批准請求裡（規則見 `references/review.md`「意見分級怎麼處理」）。使用者還沒看過這份計畫，直接改 `## 計畫 v1` 本身，不開新版本，改完記一行 `[紀錄] 依 plan-critic 修改計畫 v1：<改了什麼>`，再送一次只看改過的部分。最多兩輪；兩輪後仍有沒修掉的 blocker，把未解決意見一併列在批准請求裡交使用者決定。過了才 `--set 狀態=待批准 --set "下一步=等使用者批准計畫 v1"`。
- 高風險的批准請求除了計畫摘要，還要列 plan-critic 的結論、你採納了哪些、不採納哪些與理由。
- **回報**：依「階段回報」回報「📝 Step 3 計畫：…」，接著直接送階段 4 的批准請求。

## 階段 4：批准

- **只有明確同意才算**：「確認」「照計畫做」「OK 開始」。問句、部分回答、「嗯」都不算，先回答再追問一句：「我會照計畫 v<N> 開始：<摘要，含非阻擋型假設的預設>。確定嗎？」
- 有「未釐清（阻擋）」時，整體同意不算，要逐項回答完才算。
- 批准後：`log.js --set "批准=v1「<使用者原話>」" --set 狀態=已批准 --set "下一步=開分支並做步驟 1" "[批准 v1] 「<原話>」"`。非阻擋型假設沒被逐項回答時，紀錄寫「假設『…』未明確回答，採計畫預設」，不要寫成「使用者已同意某做法」。
- 這一條指令只做批准紀錄。開分支與改成「實作中」是階段 5 的事，另一次呼叫再做，不要用 `&&` 串在一起。
- 使用者修改計畫：追加 `## 計畫 v<N+1>`（寫明差別），`--set 計畫版本=<N+1> --set 批准=無`，重新定級（只能升不能降），再提交等批准。使用者的修正記 `[錯誤 來源：使用者 分類：需求]`。
- **批准訊息裡附帶補充**（「確認，另外請也…」）：補充只是加驗證、加證據、給環境資訊，不改做法與範圍時，追加 `## 計畫 v<N+1>` 寫明差別，`--set 計畫版本=<N+1> --set "批准=v<N+1>「原話」"`，視為已批准，直接往下，不必再問一次。補充改了做法、範圍或資料結構的，走上一條重新等批准。
- **「需要你決定」的結果要記下來**：批准後記一行 `[紀錄] 已定的決定：<每一項最後採用的做法>`（整體同意就是全採預設）。之後派給 implementer、verifier、reviewer 的 prompt 都要帶這份結果（見各模板的「已定的決定」一節），它們才知道哪些行為是使用者確認過的。
- **使用者改選「另一個選擇」**（「確認，但第 2 項用另一個」）：選項是計畫已經攤開的，不算修改計畫。追加 `## 計畫 v<N+1>` 寫明哪一項改選、受影響的驗收標準與步驟怎麼變，`--set 計畫版本=<N+1> --set "批准=v<N+1>「原話」"`，視為已批准，直接往下；高風險不用為此重送 plan-critic（它審過這個選項）。改選之後做法、範圍或等級變了，而且超出計畫「影響」欄寫到的，才走重新等批准。
- **回報**：批准請求就是這階段的回報，標題用「✋ Step 4 批准：等你確認計畫 v<N>」，停下等使用者。收到批准後回報一行「✋ Step 4 批准：已批准 v<N>」再進階段 5。

## 階段 5：實作

- 開分支 `<type>/<kebab-name>`，`--set 分支=<名稱> --set 狀態=實作中`。已在非主幹分支時問是否沿用。
- **每一步固定四拍，順序不能換、不能跨步**：
  1. 只改這一步「改哪些檔案」欄列的檔案。
  2. 跑這一步「這一步的驗證」欄寫的指令，看到結果。
  3. 記 `[完成] 步驟 N：…` 與 `[證據 標準N] …`，更新「下一步」。
  4. 中風險以上做檢查點 commit：`git commit -m "wip: 步驟 N <摘要>"`（低風險可省）。設定 `commit=off` 時略過這一拍。
  第 2 拍沒過就不進第 3 拍；第 4 拍沒做完就不碰下一步的檔案。不要「順手先寫下一步的測試」，也不要把 commit 排在驗證前面。接續時靠的是紀錄與 commit 的順序和實際一致。
- 碰到計畫沒涵蓋的情況：小偏差記 `[紀錄]` 繼續；要改做法、範圍、資料結構的，停下來重提計畫（回階段 3）。
- 實作中發現影響超出定級（例如要改有呼叫者的函式、要動 schema）：`[升級]` 記下，依 `tiering.md` 升級，告知使用者。
- 同一步驗證連續失敗 3 次 → 停，記 `[錯誤]`，回報使用者，不再硬試。高風險時 implementer 回報的失敗與你核對不過各算一次，重派不重設計數。
- 每步更新「下一步」。
- **高風險每步派 fresh implementer**：先讀 `references/implement.md`。第 1、2 拍交給 `doit:implementer` subagent（前景執行，每步一個新的，一次只派一個），輸入只有這一步的做什麼／改哪些檔案／驗證、對應的驗收標準、相關假設、已定的決定、前面步驟的產出、範圍外、專案慣例，**不給對話與你的推理**。它不 commit、不寫任務檔。回來後你自己核對（改到的檔案都在清單內、重跑驗證通過、測試斷言有效）才做第 3、4 拍；沒過就再派一個新的，不自己下場改。
- **每步回報**：四拍做完就依「階段回報」回報「🔨 Step 5 實作：步驟 N／總步數 …」，不等使用者回覆就繼續（這是透明度，不是批准點）。
- **回報**：每一步各回報一次（見上）；最後一步的回報就是這階段的回報，接著進階段 6。

## 階段 6：驗證

- 跑計畫列的所有測試與指令，結果逐條對應驗收標準記 `[證據 標準N]`。高風險另外把基準檢查列的**全部**測試跑一遍（不只相關的），記 `[證據 基準]`。
- 有 UI 改動：讀 `references/ui-verify.md`，有內建瀏覽器工具且 dev server 跑得起來就照驗收標準實際操作，證據寫網址、操作、觀察到的實際文字；跑不起來或是桌面應用就記「需使用者手動確認」加具體步驟。截圖不能單獨當證據。
- 與基準比較：新失敗一律算這次造成，除非能證明不是。
- 驗證完 `--set 狀態=待審查`，「下一步」依等級寫：低風險「檢查完成門檻後交付」、中風險「等 reviewer 結果」、高風險「等 verifier 與 reviewer 結果」。直接進階段 7，不再另設一次下一步。
- **回報**：依「階段回報」回報「🧪 Step 6 驗證：…」，接著進階段 7。

## 階段 7：審查

- **低風險**：跳過，直接進階段 8。
- **中風險**：讀 `references/review.md`，呼叫 `doit:reviewer` subagent（前景執行，等它回來），輸入只有：需求原文、計畫 vN 的做法／假設／已定的決定／驗收標準／實作步驟／範圍外、取得 `git diff <起始SHA>` 的指令（含工作目錄變更）、專案路徑與慣例。**不給實作過程、不給你的推理**。
- **高風險**：先 `doit:verifier` 再 `doit:reviewer`，都前景執行。verifier 的輸入只有：需求原文、假設、已定的決定、驗收標準表、基準檢查的指令與結果、取得 diff 的指令、專案路徑、暫存目錄路徑（給它放邊界測試腳本，不得放進專案）。結論「未通過」或有 blocker → 回階段 5 修，修完只重跑失敗的標準，最多兩輪。結論「通過」但有要修的 major，而且修正動到測試以外的程式碼 → 修完同樣重送 verifier，只重跑那條意見的重現輸入與受影響的標準。verifier 過了才呼叫 reviewer，reviewer 的 prompt 可以附上 verifier 的結論一行（不附過程）。
- **三種審查的 prompt 都把內容貼進去，不給任務檔路徑**：計畫、假設、驗收標準再長也照貼。任務檔的紀錄節有你的處理說明與先前審查的結論，審查者讀到就不獨立。
- 結果以 `[審查 reviewer @<sha>] 結論：…`／`[審查 verifier @<sha>] 結論：…` 加逐條意見記進任務檔。blocker 必須修（回階段 5 的對應步驟）；major 預設要修，不採納時要寫具體到這個專案的理由，並在交付回報裡逐條列出；minor 可修可記。完整規則見 `references/review.md`「意見分級怎麼處理」。修完只重審改過的部分，最多兩輪，之後停下交使用者。
- **高風險的審查修正也派新的 implementer**，主流程不自己改（做法見 `references/implement.md`「審查後的修正」）；低／中風險由主流程自己改。
- **審查後的修正不做 wip commit**，留在工作目錄，等門檻通過後進交付 commit。這樣交付 commit 一定有內容，也不需要改寫已有的 commit。
- **回報**：依「階段回報」回報「👀 Step 7 審查：…」；低風險標題寫「低風險，跳過」，內容仍用五欄模板。接著進階段 8。

## 階段 8：完成

完成門檻（全部成立）：每條驗收標準有證據；基準檢查沒有新失敗；審查沒有未處理的 blocker 或 major（blocker 都已修；major 不是已修就是記了不採納理由。中風險看 reviewer，高風險看 verifier 與 reviewer 兩者）；工作目錄沒有計畫沒提到的檔案變更。任務檔所有 `[範圍外]` 行要在交付回報裡逐條列出。

門檻過後先 `--set 狀態=完成 --set "下一步=無（已完成）"`，再依設定交付（設定以階段 0 或接續時讀到的為準）。

**`commit=on`（預設）**：狀態改完後，**另一次呼叫**做交付 commit `<type>: <摘要>`。不能用 `&&` 串在同一條指令，因為 hook 在整條指令執行前就依舊狀態判定，會連狀態更新一起擋下。

- 工作目錄有未 commit 的變更（審查修正、最後一步）→ 全部進交付 commit。
- 沒有任何未 commit 變更（審查無意見、每步都做了 wip）→ `git commit --allow-empty`，訊息同樣寫 `<type>: <摘要>`，內文註明「完成門檻通過；變更在前面的 wip 檢查點」。
- **不要**用 `git reset --soft` 改寫既有 wip commit。檢查點保留，squash 由使用者在 merge 時決定。

**`commit=off`**：不做任何 commit。交付回報列出 `git status --porcelain` 的所有檔案，並建議一個 commit 訊息 `<type>: <摘要>` 讓使用者自己 commit。

**PR**：
- `pr=on`：有 remote 時 push 分支並用 `gh pr create` 開 PR，PR 內文寫做了什麼、驗收證據、範圍外。沒有 remote、沒有 `gh` 或被權限擋下時不另想辦法，改回報分支名稱與失敗原因。
- `pr=off`（預設）：不 push、不開 PR，回報分支名稱讓使用者自己決定。

**任務來自計畫檔時**：交付後用 Edit 把計畫檔任務清單裡這個任務的狀態改成「完成」；所有任務都完成時，把計畫檔頂端的狀態也改成「完成」。交付回報的「需要使用者接手」列出下一個可以做的任務（依賴都已完成的第一個）與它的 `/doit:go` 指令。實作中發現計畫檔的假設或拆法不成立，在計畫檔「變更紀錄」加一行說明，並在交付回報告訴使用者哪些後續任務受影響；不要自己改寫後續任務。
- **回報**：交付回報就是這階段的回報，標題用「📦 Step 8 完成：…」，接著進階段 9。

## 階段 9：檢討

中風險與高風險每次做；低風險只在有 `[錯誤]` 時做。讀 `references/retro.md`，把任務檔裡每個 `[錯誤]` 變成一條預防規則，用 `log.js --lesson project|global` 搭配 heredoc 寫進對應教訓檔；教訓檔裡已有同一個坑時改用 `log.js --lesson-bump global G-001`（再犯）或加 `--hit`（踩到既有問題），不重建條目也不手改次數。全域檔在 `~/.doit/LESSONS.md`，在專案目錄外，不要直接 Write 或 Edit。
- **回報**：依「階段回報」回報「🪞 Step 9 檢討：…」；不需要檢討時寫原因（例如「低風險且沒有 [錯誤]」）。這是整個任務的最後一份回報。
